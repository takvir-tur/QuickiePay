Section 01

What is QuickiePay?

QuickiePay is a Mobile Financial Service (MFS) platform — similar to bKash or Nagad — designed as a database-driven academic project. It demonstrates core DBMS concepts: normalization, referential integrity, transactions (ACID), role-based access, and auditing.

📱 Five User Roles

Personal (Customer), Agent, Merchant, Biller, and Admin — each with dedicated tables following a Specialization/Generalization hierarchy.

💸 Seven Transaction Types

Send Money, Cash In, Cash Out, Merchant Payment, Bill Payment, Add Money, and Mobile Recharge — all recorded atomically.

🛡️ Admin & Audit

Super Admins can freeze accounts, reverse transactions, manage fraud alerts, and every sensitive action is logged to audit_logs.

15+ tables defined in SQL/schema.sql. Uses UUIDs, ENUM types, CHECK constraints, foreign keys with cascade/restrict rules, and indexed columns.

📂 How the Folders Map to the Architecture

client/app/ → Next.js pages that make fetch() calls to the Express API.
database/routes/ → Express Router files that define URL patterns like /api/auth/login.
database/controllers/ → Handler functions containing the actual SQL queries via pool.query().
database/middleware/ → verifyToken decodes JWTs; verifyAdmin checks the role.
database/utils/ → Shared helpers like configHelper.js (reads system_settings) and auditLogger.js (writes audit_logs).

Section 04

Specialization / Generalization

This is the most important DBMS concept in QuickiePay. The users table is a supertype, and each role (Personal, Agent, Merchant, Biller, Admin) is a subtype with its own table.

🏗️ How It Works in the Database

Every person who signs up gets a row in users (the supertype table) and a row in accounts (their wallet). Then, based on their chosen role, exactly one additional row is inserted into the corresponding subtype table:

  • PERSONAL → row in personal_accounts (status only)
  • AGENT → row in agents (business_name, commission_rate, approved_by)
  • BUSINESS → row in merchants (business_name, trade_license, approved_by)
  • BILLER → row in billers (approved_by) + row in services (service_name, organization_name)
  • ADMIN → row in admins (role, permission_level) — inserted directly in DB, not via registration

🔑 Key DBMS Concept: The 1:1 Relationship

Each subtype table has a user_id column that is both a FOREIGN KEY referencing users(user_id) and a UNIQUE constraint. This enforces a strict 1:1 relationship — one user can only appear in one subtype table.

📝 How It Works in the Code (Registration Flow)

The registerUser() function in authController.js uses a PostgreSQL transaction (BEGIN → COMMIT / ROLLBACK) to atomically insert across multiple tables:

await pool.query('BEGIN'); // 1. Insert into the supertype table await pool.query(`INSERT INTO users (...) VALUES (...)`); // 2. Create the wallet await pool.query(`INSERT INTO accounts (user_id, account_type) VALUES ($1, $2)`); // 3. Insert into the correct subtype table based on account_type if (account_type === 'PERSONAL') await pool.query(`INSERT INTO personal_accounts (user_id) ...`); else if (account_type === 'AGENT') await pool.query(`INSERT INTO agents (user_id, business_name, ...) ...`); else if (account_type === 'BUSINESS') await pool.query(`INSERT INTO merchants (user_id, business_name, ...) ...`); else if (account_type === 'BILLER') { await pool.query(`INSERT INTO billers (user_id) ...`); await pool.query(`INSERT INTO services (biller_id, ...) ...`); } await pool.query('COMMIT'); // All-or-nothing

If any INSERT fails (e.g., duplicate phone number, constraint violation), the entire operation is ROLLBACKed — no partial data is ever saved. This is the Atomicity property of ACID.

Section 05

Transaction Types & Supertype/Subtype

Just like users, transactions also follow a Supertype/Subtype model. Every financial operation writes a row to the common transactions table, and type-specific details go into a subtype table.

💸

Send Money

Person → Person. Only the supertype transactions table is used. Flat fee applied.

🏧

Cash In

Agent → Customer. Subtype: cash_transactions with cash_type = 'CASH_IN'. No commission.

💵

Cash Out

Customer → Agent. Subtype: cash_transactions with cash_type = 'CASH_OUT'. Commission charged.

🛒

Merchant Payment

Customer → Merchant. Subtype: payment_transactions with merchant_id and optional invoice_number.

📄

Bill Payment

Customer → Biller. Subtype: bill_transactions with biller_id, billing_month, due_date.

🏦

Bank Transfer

Biller → Bank (payout). Recorded in custom biller_bank_transfers table alongside a transaction record.

💡 Why Supertype/Subtype for Transactions?

The common transactions table stores shared fields (sender, receiver, amount, fee, status, time) so we can run global queries like "total daily volume" or "all failed transactions" with a single SELECT. The subtype tables only add role-specific metadata (e.g., which agent handled a cash-out, which biller received a bill payment). This avoids NULL-heavy designs and adheres to 3NF normalization.

Section 06

Data Flow — Send Money

A step-by-step breakdown of what happens when a user sends ৳1,000 to another user. This is the core demonstration of ACID transactions and deadlock prevention.

1

Frontend → POST /api/transactions/send

The Next.js page sends { receiver_phone, amount, pin } with a JWT Bearer token in the Authorization header.

▼
2

Middleware: verifyToken

jwt.verify() decodes the token, extracts user_id, checks if the user is BLOCKED by querying all subtype tables with COALESCE, and attaches req.user.

▼
3

Controller: Verify PIN

JOINs users ↔ accounts to get the sender's pin_hash and account_id. Uses bcrypt.compare(pin, pin_hash) to verify.

▼
4

Lookup Receiver

Queries users ↔ accounts by phone_number to get the receiver's account_id. Checks sender ≠ receiver.

▼
5

System Config & Limit Checks

getSystemConfigs() reads the system_settings table. Checks: amount ≤ MAX_PER_TXN_LIMIT, daily total + amount ≤ DAILY_TXN_LIMIT.

▼
6

BEGIN Transaction + Lock Accounts

BEGIN starts a PostgreSQL transaction. Both accounts are locked with SELECT ... FOR UPDATE in sorted order to prevent deadlocks. Re-checks balance after lock.

▼
7

Execute Double-Entry Updates

UPDATE accounts SET balance = balance - (amount + fee) WHERE sender
UPDATE accounts SET balance = balance + amount WHERE receiver

▼
8

INSERT into transactions

A new row is written to the transactions supertype table with type = 'SEND_MONEY', status = 'SUCCESS', and a unique reference_no.

▼
9

COMMIT

If everything succeeded, COMMIT makes all changes permanent atomically. If any step failed, ROLLBACK undoes everything.

Section 07

Data Flow — Cash Out

Cash Out involves a Customer and an Agent, uses the cash_transactions subtype table, and involves a commission calculation. It writes to three database tables in a single atomic transaction.

1

Verify Customer PIN + Find Agent by Phone

JOINs across users → accounts for the customer, and users → accounts → agents for the agent. Checks agent is ACTIVE.

▼
2

Calculate Fee & Check Limits

fee = amount × CASH_OUT_FEE_PCT / 100 (from system_settings). Checks per-txn limit and daily limit.

▼
3

BEGIN + Lock + Balance Update

Customer balance decreases by (amount + fee).
Agent balance increases by (amount + fee) — the agent keeps the fee as commission.

▼
4

INSERT into transactions (Supertype)

Records the base transaction with type = 'CASH_OUT', the amount, and the fee.

▼
5

INSERT into cash_transactions (Subtype)

Adds the Cash Out-specific details: agent_id, cash_type = 'CASH_OUT', commission. Uses the same transaction_id as the PK/FK.

▼
6

COMMIT

Three tables modified atomically: accounts (×2 UPDATEs), transactions (INSERT), cash_transactions (INSERT).

Section 08

Authentication & Security

QuickiePay uses JWT (JSON Web Tokens) for session management and bcrypt for PIN hashing. The database never stores plaintext PINs.

🔐 Login Flow

  1. User submits phone + PIN
  2. Server queries users JOINed with admins, accounts, and all subtype tables
  3. Checks if account is BLOCKED (from subtype status)
  4. bcrypt.compare(pin, pin_hash) — constant-time comparison
  5. On success, jwt.sign() generates a token with: user_id, phone, role, isAdmin
  6. Token is sent to the client, stored in localStorage, and sent with every future API call

🛡️ Middleware Pipeline

Every protected route passes through this pipeline:

// Route definition in adminRoutes.js: router.get('/dashboard', verifyToken, // ① Decodes JWT, checks if BLOCKED verifyAdmin, // ② Checks req.user.role === 'SUPER_ADMIN' getAdminDashboardData // ③ The actual handler );

verifyToken runs a SQL query to check the user's status across all subtype tables using COALESCE. If status is 'BLOCKED', access is denied — even with a valid token.

Section 09

Admin Panel & Operations

The Super Admin has a full dashboard with real-time statistics, user management, a global ledger, fraud detection, and system configuration.

📊 Dashboard Aggregation

The getAdminDashboardData() function runs 5 queries in parallel using Promise.all():

  • COUNT of active users across all subtype tables
  • SUM(balance) from all accounts
  • SUM(amount) from last 24h successful transactions
  • COUNT of unreviewed risky transactions
  • Latest 10 transactions with receiver details

🧊 Freeze / Unfreeze Accounts

toggleUserStatus() dynamically determines which subtype table to update based on account_type, then flips the ENUM between 'ACTIVE' and 'BLOCKED' using a CASE expression.

🚨 Fraud Alert Detection

Alerts are identified using SQL conditions. The query flags transactions where:

  • amount ≥ 50,000 (unusual volume) or amount ≥ 100,000 (velocity spike)
  • transaction_status = 'FAILED' (suspicious failure)
  • is_risk_reviewed IS NULL OR FALSE (not yet reviewed)

↩️ Transaction Reversal

Inside a single PostgreSQL transaction:

  1. Fetches the transaction with FOR UPDATE row lock
  2. Checks it's not already CANCELLED or FAILED
  3. Deducts amount from receiver, refunds amount + fee to sender
  4. Sets status to 'CANCELLED'

🔗 Foreign Key Design in audit_logs

All three FKs (admin_id, affected_user_id, transaction_id) use ON DELETE SET NULL. This means if an admin or user is deleted, the audit record is preserved but the FK is set to NULL — the audit trail is never lost.

Section 12

Concurrency Control & ACID

QuickiePay implements robust concurrency handling to prevent race conditions, deadlocks, and double-spending.

🔒 Pessimistic Locking

Before modifying any account balance, the code acquires an exclusive row-level lock using SELECT balance FROM accounts WHERE account_id = $1 FOR UPDATE.

This prevents two concurrent transactions from reading the same balance before either has updated it (the lost update anomaly).

🔀 Deadlock Prevention

When two accounts must be locked (sender + receiver), they are sorted alphabetically before locking:

const accountsToLock = [senderAccountId, receiverAccountId].sort(); await client.query('SELECT ... FOR UPDATE', [accountsToLock[0]]); await client.query('SELECT ... FOR UPDATE', [accountsToLock[1]]);

If Txn A (User1→User2) and Txn B (User2→User1) run simultaneously, both lock in the same order — no circular wait, no deadlock.

⚛️ Atomicity — BEGIN / COMMIT / ROLLBACK

Every financial operation wraps its queries in a PostgreSQL transaction block. If the Node.js process crashes mid-operation, the database automatically rolls back the incomplete transaction.

🏊 Connection Pooling

For multi-step transactions, the code uses pool.connect() to get a dedicated client (not the shared pool), ensuring all queries within a BEGIN...COMMIT block run on the same connection. The client is always released in a finally block.
